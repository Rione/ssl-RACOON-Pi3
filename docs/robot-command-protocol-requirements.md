# ロボット指令プロトコル 要件メモ

**宛先**: 指令プロトコルを実装する人
**発信**: 自己位置推定・位置制御（Rock5A / Go）側
**関連**: [`docs/self-localization-plan.md`](./self-localization-plan.md)

これは**要件だけ**をまとめたものです。「推定側が何を受け取れば動くか」「何を返したいか」だけを書いていて、
実現方法（protobuf か独自バイナリか、既存フレームの拡張か新設か）は実装する人に任せます。

---

## 0. 前提として知っておいてほしいこと

```
  SSL-Vision ──マルチキャスト直送──► ロボット        （既存。触らない）
  RAVEN ──────目標位置──────────────► ロボット        （★ 新設が必要）
  RAVEN ◄─────自己位置推定──────────  ロボット        （★ 新設が必要）
```

**RAVEN は自機について独自の位置推定をやめ、ロボットが返す推定をそのまま採用する方針です。**

つまり上りの推定値は「参考情報」ではなく、**RAVEN の世界モデルそのもの**になります。
欠測・遅延・精度がそのまま AI の判断に効くので、下の §3 と §5 を特に見てほしいです。

---

## 1. 下り: 目標位置（RAVEN → ロボット）

位置制御ループは Rock5A 上で回ります。RAVEN は目標を送るだけです。

| フィールド | 型の目安 | 単位 | 必須 | 備考 |
| --- | --- | --- | --- | --- |
| `robot_id` | uint8 | — | ✅ | |
| `target_x` / `target_y` | int16 or float | **mm** | ✅ | ワールド系（SSL-Vision 準拠、フィールド中央原点） |
| `target_theta` | int16 | **mrad** | ✅ | 正規化（±π 折り返し）は受信側でやるので不要 |
| `target_vx` / `target_vy` | int16 | mm/s | 任意 | ロボット系。フィードフォワードに使う。**あると追従精度が上がる** |
| `target_omega` | int16 | mrad/s | 任意 | 同上 |
| `mode` | uint8 | — | ✅ | 位置制御 / 速度制御 / 停止 の区別 |
| **`stamp`** | uint32 or uint64 | **µs または ns** | ✅ | **§2 を読んでほしい** |
| `seq` | uint16 | — | ✅ | 欠落・順序逆転の検出に使う |

---

## 2. タイムスタンプについて（いちばん大事）

**`stamp` を必ず載せてください。**「この目標はいつ時点の計画か」が分かれば十分です。

- **送信側の単調時計でかまいません。**壁時計に合っている必要はありません。
  ロボット側でオフセットとスキュー（水晶の周波数差）を推定して、自分の時間軸に写します。
- **精度も要りません。**単調に増えて、送信側の中で一貫していればそれでよいです。
- **一番困るのは「時刻が無い」ことです。**
  到着時刻しか手がかりがないと、**無線のジッタ（バースト的に数十 ms 伸びる）がそのまま目標の時刻誤差**になります。
  ロボットが 3 m/s で走っているとき、30 ms の時刻誤差は 9 cm の位置誤差に相当します。

同じ理由で、**上りの推定にも `stamp` を必ず載せます**（その推定がどの瞬間の値かを RAVEN が知るため）。

## 4. 共分散と `health` を必ず載せてほしい理由

RAVEN が自機の推定をロボット任せにする以上、
**「この値をどれだけ信じてよいか」が一緒に来ないと、壊れたときに RAVEN 側が気づけません。**

具体的には次の 3 つが起こり得ます。

- **vision が長時間見えていない** — オドメトリだけで推定が伸びていき、じわじわずれる。
  `since_vision_ms` と共分散の増大でこれが見えます。
- **無線のマルチキャストが落ちている** — SSL-Vision はロボットへ直送で、ACK も再送もありません。
  欠落が続けば `health = DEGRADED` にします。
- **フィルタが発散した / NaN が出た** — `health = INVALID` にします。

`health = INVALID` のときは **RAVEN 側が vision 生値にフォールバックできる**設計にしたいです。
この切り替え条件を明示的に持てるかどうかが、この方針を安全に成立させる鍵になります。

## 5. レート・遅延・信頼性の要件

| 項目 | 要件 | 理由 |
| --- | --- | --- |
| 下り目標位置のレート | **60 Hz 程度**（RAVEN の制御周期に合わせる） | ロボット側は 125 Hz で内挿するので、これ以上速くなくてよい |
| 下りの許容欠落 | **連続 3 フレームまで** | それを超えたら減速・停止へフォールバックする |
| 上り推定のレート | **60 Hz で十分**（125 Hz は不要） | RAVEN の世界モデル更新が 60 Hz なので |
| 片道遅延 | 小さいほどよいが、**一定であることの方が大事** | 変動は補償できないが、一定なら予測で消せる |

**帯域は問題になりません。** 1 台あたり上下とも 30 バイト × 60 Hz ≒ 2 kB/s、11 台でも 22 kB/s 程度です。
**軽くするより、時刻と共分散を載せる方をはるかに優先してください。**

## 6. やらないでほしいこと

### タイムスタンプを付けずに送る
§2 の通りです。これだけは避けたいです。

### 送信側で平滑化・補間してから送る
推定側がもう一度フィルタに通すので、**二重にフィルタがかかって統計的に不正になります。**
具体的には、観測が白色でなくなり、同じ情報が 2 回効いて**共分散が実際より小さく出て**（＝推定が過信し）、
さらに遅れが二重に積み上がります。

**生の値をそのまま、時刻付きで送ってください。**平滑化はこちらでやります。

### TCP で信頼配送にする
再送で遅延が跳ねるより、**落ちた方がマシ**です。古い目標位置は使わないので、再送されても価値がありません。
**UDP ＋ シーケンス番号**で十分です。

### 可変長にして詰める
固定長の方がデバッグが楽です。§5 の通り帯域は問題になりません。

### エンディアンを混ぜる
既存が little endian なので揃えてください。

### 単位を暗黙にする
**フィールド名に単位を入れてください**（`target_x_mm`、`omega_mrad_s` のように）。

> このプロジェクトでは既に「変数名は `FlWheelSpeedRadS` なのに中身は m/s」という事故が起きていて、
> 実際に誤差の切り分けを難しくしています。名前に単位を書くだけで防げます。

## 7. 既存の通信との関係

| 方向 | 現状 |
| --- | --- |
| 下り（RAVEN → ロボット） | UDP **20011**。1 バイトヘッダ（上位 4bit = robot_id、下位 4bit = command_id）+ protobuf。`0x06` が DATA（`grSim_Robot_Command`、**速度指令のみ**） |
| 上り（ロボット → RAVEN） | マルチキャスト **224.5.69.4:16941**。1 バイトヘッダ + `PiToMw` protobuf |
| vision | マルチキャスト **224.5.23.2:10694**（SSL-Vision → ロボットへ直送）。**触らない** |

考えられる実装の方向（判断は任せます）:

- **下り**: `0x06` を壊さないよう、**新しい command_id を切る**のが安全だと思います。
- **上り**: `PiToMw` に message を足すのが素直です。
  ただし **`PiToMw` は現状「状態通知」用**で、60 Hz で回す前提の設計になっていません。
  レートを上げるか、推定だけ別経路にするかは判断が要ります。

---

## 8. 決まると嬉しい順

1. **`stamp` を載せられるか** — 載せられない場合、精度目標（位置 RMSE 10 mm）を下げる必要があります。
2. **上りに共分散と `health` を載せられるか** — RAVEN 側のフォールバック設計に直結します。
3. **フィールド配置の確定** — ここは後からで大丈夫です。
   こちら側は JSON のプロファイルで吸収できる作りにするので、決まった時点で設定を書き換えるだけで追従できます。

質問があれば聞いてください。こちらの都合で決め打ちしたくないので、
「この形なら作れる」という案があれば、それに合わせて推定側を調整します。
