## 3. PoC の構成 (詳しくは traj-poc.md)

```
traj_gen (PC) ──JSON Lines + END──> ssh ──> racoon-pi3 -trajpoc (ロボット)
                                            ├ SSL-Vision を直接受信 (青 12)
                                            ├ 125 Hz で手法の速度 → link.SetVelocityOverride → SPI
                                            └ 指標を表示 + CSV / ログを /root/trajpoc に保存
```

- 点の中身は RAVEN の `TimedTrajectoryPoint` と同じ (x, y [mm], theta [rad], t [ns])。t は先頭からの相対、座標は開始姿勢に対する相対
- 軌道の形: line / square / circle / fig8 / **turn (その場で回る。size=角度 rad、speed=角速度、accel=角加速度)** / **hold (止まったまま size 秒)**
- 手法: `p` (位置 P) / `ffp` (参照速度の先回し + P) / **`ffp_vlead` (速度の先回しだけ `-trajlead` 先)**。
  **2026-09-23 に master の新しい構成へ移した**: 参照の補間と追従の計算は本番の `internal/control`、安全の判定は `internal/supervisor`。
  PoC に残したのは軌道生成・記録・指標・止まり際の試作だけ。手法は「先回しの有無 (ノードの速度を 0 にするか)」と
  `control.Config.VelocityLead` で表す。位置まで先読みする `ffp_lead` と hermite 補間は、効果が無かったので消した
  (机上の数字は移す前と一致: p 118.9 mm・遅れ 275 ms、ffp 27.3 mm・30 ms、ffp_vlead 22.8 mm・−8 ms)
- 既定: Kp 3.0, Kth 4.0, 先読み 30 ms, 上限 0.5 m/s・2.0 rad/s・2.0 m/s²、枠 1.0 m (+0.2 m で打ち切り)、vision 250 ms で 0・1 s で打ち切り
- 回し方 (いつもこの形で回している):
  ```bash
  cd /home/zyro/ssl_ws/java/ssl-RAVEN/ssl-RACOON-Pi3
  export PATH=~/sdk/go1.27.1/bin:$PATH GOPATH=~/go GOCACHE=~/.cache/go-build ROBOT=172.15.0.34 VISION_IFACE=wlan0
  scripts/trajpoc.sh deploy        # コードを変えたら

  scripts/trajpoc.sh restore       # 終わったら Pi2 に戻す
  ```

## 5. 分かったこと

1. `p` の遅れ 294 ms は理論 (1/Kp = 333 ms) と机上シミュレーションの予測 (276 ms) に近い。**仮の機体モデルは大筋で当たっている**
2. 参照速度を先回しすると遅れはほぼ消える (位置誤差 49 → 10〜12 mm)。同条件の繰り返しの差は約 2 mm (測定のばらつきの目安)
3. 先読み 30 ms は効きすぎ (往復で +21 → −11 ms、円で −1 → −25 ms)。0.2〜0.4 m/s では `ffp` の遅れ自体が 0〜20 ms しかない
4. **`p` の方が経路の形からのずれ (輪郭・横ずれ) は小さい** (往復で 3.7 対 7〜8 mm)。速度の先回しで走り出しから全速の指令が出ることと、向きのぶれ (最大 4〜7°) が関係していそう
5. **円では時刻どおりに回れているのに、ひと回り大きい円 (+13 mm) を回る**。遅れのせいではない (遅れ ≒ 0)。先読みを足しても変わらない
6. 向きを変えない軌道なのに向きが最大 4〜8° ぶれる。並進で機体が回され、向きの P (Kth 4) が後から戻している
7. **円の外への膨らみは「速度指令の向きが遅れて効く」ことが原因** (横滑りではない)。
   - 8 の字で左右どちら回りでも外 → 向きの推定・座標変換の偏りではない
   - 膨らみは速度の 2 乗に比例。**ただしこれは遅れでも横滑りでも同じ形になる** (外向きの速度 v·(v/R)·遅れ を P が押し戻すので
     ずれ = v²·遅れ/(R·Kp))。円の上で「指令と実際の向きのずれ」から遅れを逆算しても、定常ではどちらの原因でも式に合ってしまうので証拠にならない
   - 決め手: 速度の先回しだけを先読みする `ffp_vlead` で膨らみが消えた (+13.8 → −1.4 mm)。横滑りなら指令の向きを変えても消えない
   - 膨らみが 0 になる先読みは約 90 ms で、往復の直線で独立に測った遅れ 95〜110 ms と合う
   - 効果: 位置誤差 20 → 13 mm、輪郭誤差 16 → 9 mm、横ずれ 17 → 9.5 mm
8. つまり **速度で指令する限り、FF の速度は「指令が効くまでの遅れ」だけ先の参照から取るのが正しい**。
   位置の目標まで先にずらす `ffp_lead` はこれと別物で、先走るだけで膨らみは直らなかった
9. **最良の先読みは 80〜90 ms** (#10〜14)。120 ms では内へ切れ込む。8 の字の左右どちら回りでも、
   往復の直線でも良くなる (往復: 位置誤差 10.5〜12.4 → 8.9 mm、輪郭誤差 7〜8 → 4.6 mm)。
   直線の加減速にも同じ遅れが効いていた
10. 代わりに**到着の精度が少し落ちる** (往復 0.2 → 3.1 mm、8 の字で最後に向き 3.2° 残る)。止まり際まで速度を先回しし、
    P の詰めが相対的に弱い。**止まり際 (軌道の末尾の先読み区間) だけ先読みを外す**などの手当てが要りそう
11. **vision はとてもきれい**: 位置の細かい揺れ 0.2〜0.4 mm RMS・向き 0.25〜0.32°、約 116 Hz、最大の途切れ 17〜34 ms
    (2 次式で 150 ms 窓を当てはめた残差)。**残っている ±15 mm の揺れや最大 9° の向きのぶれは測り間違いではなく、
    ロボットが本当にそう動いている**。フィルタでは消えず、制御で直すしかない。
    → **この環境では EKF の「雑音をならす・途切れを埋める」効果はほぼ無い** (ユーザーに「EKF は要らないか」と聞かれての確認)。
    EKF が要るのは (1) 位置の帰還の遅れを「今」の予測で埋めたいとき (2) 試合の隠れ・途切れ・複数カメラ (3) モデルを使う制御。
    (1) は EKF の手前に、vision + 直近 90 ms の指令の積分で今の位置を予測する (スミス予測) 安い手がある。
    `ffp_lead` は vision の古さを 4 ms 前後としか見ておらず (timesync の写像は一定の片道遅れを含まない)、
    肝心の一定の遅れを外挿していなかったので効かなかったと考えられる
13. **向きのぶれ (C) の解析** (`scripts/trajpoc-heading.py`、ロボットは動かさず記録だけ):
    - 並進の加速度・速度では説明できない (R² 0.07〜0.26、係数の符号が走りごとにばらばら)。「回りながら指令がずれて横ずれ」も相関が弱い
    - 時系列を見ると**向きの制御が振動している**。止まった後 (並進 ≒ 0) でも ±5° で振動が続く
    - 往復の直線では振動の 80〜93% が 1〜4 Hz (ピーク 1.7〜2.6 Hz)。向きの P (Kth 4、遅れ 100 ms、倍率 1) なら 0.6 Hz 前後でよく減衰するはずで、
      2 Hz で振動するには**輪の実質のゲインが 2.5〜3 倍**要る
    - 閉ループの記録から「実際の角速度 / 指令」を当てはめると、往復の直線 5 本で **×2.2〜2.4・遅れ 90〜110 ms** と揃う (円・8 の字はばらつく)
    - ただし **RAVEN が開ループで同定した `gain_omega` は 9 台すべて 0.91〜1.0**。閉ループの推定は偏り得るので、上の ×2.3 は未確定。
      **テスト機 (MAC 20:bd:1d:d7:3f:f2) は RAVEN の同定に入っていない**ので、この機体だけずれている可能性はある
    - 円・8 の字には別に 0.3 Hz 前後のゆっくりした向きのずれ (進む向きにつられる分) も混ざる
    → **開ループの試験 (#17, 11:13, `-shape turn -size 1.5708 -speed 1.0 -accel 3.0 -trajkth 0`) で倍率の説は否定**:
      実際の回転 85.0° / 参照 90° = 0.944、角速度の当てはめ ×0.972 (R² 0.93)。RAVEN の gain_omega と一致。**閉ループの ×2.3 は偏った推定だった**
    - 回転も約 90 ms 遅れて効く (一定の 57°/s で角度が 4〜6° 遅れる)。「遅れ 15 ms・頂点が 68 ms 早い」は角速度を微分したときの雑音による見かけ

## 7. 安全と、はまった所

- **STM に指令途絶のタイムアウトが無い**。Pi のプロセスが死ぬと最後の速度で走り続ける。人がそばにいるときだけ走らせる
- 開発ビルドは `v0.0.0-…+dirty` という版になり、**以前は自己更新の「開発版」判定をすり抜けていた** (`a664554` で修正、PoC 中は自己更新を起動しない)。
  リリースが出た後だと走行中に上書き → os.Exit で即死していた
- Go は既定で SIGPIPE で即死するので PoC では無視している
- `pgrep -f` / `pkill -f` はパターンが自分のコマンド行にも一致し、**自分のシェルを殺した** (2 回)。プロセスは `ps -eo pid,comm,args` で comm を見て選ぶ
- スクリプトで標準入力を開けておく `sleep` が標準エラーまで握ると、手元のパイプが閉じず戻らない (名前付きパイプ + trap に修正済み)
- Ctrl+C で止めると止まった理由が手元に届かない。ロボット上の `/root/trajpoc/trajpoc-<時刻>.log` を見る (`fetch` で集まる)
- **止める仕組みは実機で確認済み**: 途中で手元の ssh を SIGINT → ロボットは標準入力の EOF で直ちに停止処理を通って終了 (軌道 5.7 s のうち 1.35 s で停止)
- ID 15 が 2 台いるので RAVEN のハンドシェイクが取り合いになる。PoC 中は RAVEN との接続処理を起動しないようにした (`aa62de4`)。恒久的にはどちらかの DIP を変える
- GitHub API の未認証の回数制限 (60/h、会場の共通 IP 133.19.169.1) に当たっていた。全機の起動時の自己更新確認で食い合う
