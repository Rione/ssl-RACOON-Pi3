# RACOON 自己位置推定 — 現況と今後

**対象読者**: この作業を引き継ぐ人（人間・AI を問わず）
**最終更新**: 2026-09-13
**ブランチ**: `feat/self-localization`

---

## 0. 3 分で把握する

**やっていること**: Rock5A 上に Go で自己位置推定を実装している。
STM から届く 4 輪速度と、SSL-Vision からロボットへ直送される絶対座標を融合し、
カメラ単体より高精度・低遅延・欠落耐性のある推定を作る。

**現在地**: **推定器は動いている。ただし実機では一度も動かしていない。**
計画書のフェーズで言えば **P0〜P4 が実装済み**、P5 以降は外部要因で止まっている。
数字はすべて合成データのもので、実機の保証ではない。

**次にやるべきこと**: 優先度順に 3 つ。

1. **実機で P1 を回す**（§6.1）— 符号・ホイール順序・vision の定数遅延が決まる。
   ここが埋まるまで精度の議論は成立しない。
2. **`cmd/loc_replay` を作る**（§6.2）— 実機ログを推定器へ流し直す道具。
   これが無いと P1 で録ったログをフィルタの改善に使えない。
3. **RTS スムーザを作る**（§6.2）— 実機には真値が無いので、
   平滑化結果を疑似真値にする。これが無いと実機で精度を測れない。

**一番効くと分かったこと**: フィルタの洗練ではなく、
**vision の片道遅延の定数分を実測すること**（§5.2）。速度域の誤差はほぼ全部これだった。

## 3. 設計と、その理由

### 3.1 状態の持ち方

```
公称状態   theta (ワールド姿勢), p (ワールド位置), V (ワールド速度),
           omega (ヨーレート), s (ロボット系スリップ速度)
誤差状態   [dPhi, dP(2), dV(2), dOmega, dS(2)]  = 8 次元
```

計画 §4.2 の 10 次元から **ジャイロバイアス `b_omega` を落とし、`omega` を入力ではなく
状態に昇格させてある**。IMU が存在せず、ジャイロを予測の入力にできないため。
IMU が載ったら `Estimator.AddImu` の中身を書いて元の設計へ戻せるよう、入り口だけ先に決めてある。

**速度をワールド系で持つのが部分不変（PIEKF）の肝である。** 位置の誤差伝播が

```
d(dP)/dt = dV
```

となり、**推定値（`theta` や `V`）に一切依存しない**。ロボット系で持つと
`d(dP)/dt = R(theta)·dV + J·R(theta)·V·dPhi` となって推定軌道に依存し、
共分散が推定の出来不出来に引きずられる。位置は誤差が一番育つ経路なので、
ここを推定非依存にすることが一貫性に効く。

姿勢は SO(2) なので**左不変と右不変が一致する**（2 次元の回転は可換）。
誤差の注入が単なる加算 + 折り返しで済み、**共分散のリセット変換も恒等になる**。
3 次元なら `J = I − 0.5·[dPhi]×` を掛ける必要がある。

共分散更新は **Joseph 形式**。素朴な `(I−KH)P` より演算は多いが、対称性と正定値性が保たれる。
共分散が壊れると NEES が意味を失い、位置制御が信じてはいけない値を信じる。

### 3.2 時刻の扱い

**`CLOCK_MONOTONIC` を唯一の基準にする。** `localization.Stamp` がそれで、
プロセス起動時刻を原点とする単調時刻である。

- `time.Time` を API 境界に出さない。単調時計の読み値が JSON / gob へのマーシャルや
  `Round(0)` で落ちるため。
- `localization` と `timesync` は **`time.Now()` を呼ばない**。すべて `Stamp` を引数で受ける。
  同じ入力から必ず同じ出力になることが、オフラインチューニングと回帰テストの前提。
- SPI の転送時刻は `conn.Tx()` の**直前・直後の中点**。`time.Ticker` の公称 8 ms は、
  受信が遅れると間隔を詰めたりティックを落としたりするので信用しない。
- MCAP には「壁時計 epoch」と「単調時計」の組を起動時に 1 度だけ書く。
  読む側はこれで RAVEN のログへ引き直せる。

**vision のクロック写像**は下側凸包で行う（`internal/timesync/convexhull.go`）。

点群 `(t_capture, t_arrive − t_capture)` の下側凸包の傾きがスキュー、切片がオフセットになる。
片方向遅延は非負で上側に長い裾を持つので、**平均ではなく最小値が真値に近い**。

実装上、**LP ソルバは要らない**。目的 `Σ(y_i − (a·x_i + b))` の最小化・制約 `a·x_i + b ≤ y_i` は、
目的関数が `a·Σx + n·b` なので「**重心の x での直線の値の最大化**」と等価で、
その最適解は**重心の x を跨ぐ下側凸包の辺そのもの**になる。O(n log n) で数値的にも安定する。

`t_capture` は vision PC の起動からの秒で ns にすると 1e14 になるので、
最初の観測を epoch にして差分で当てはめる。

**`camera_id` ごとに独立した推定器を持つ**（`MultiSync`）。
カメラごとに露光から送信までの処理遅延が違うので、混ぜると凸包の下端が一番速いカメラに引きずられる。

### 3.3 STM フレームのデコード

バイト配置を**コードに焼かず JSON のプロファイルで駆動する**（`internal/stmframe/profiles/`）。
IMU のバイト配置とスケールが未定なので、決まった時点でプロファイルを書き換えるだけで追従でき、
**過去に記録した生フレームも再デコードできる**。

`rock5a-v1`（現行、IMU なし）と `rock5a-v2-imu`（IMU 想定）を同梱してある。
定義されていないフィールドはセンサ非搭載として扱い、上位はその観測を単に使わない。

### 3.4 ログ

MCAP（`github.com/foxglove/mcap/go/mcap`）。RAVEN の `foxglove/McapWriter.java` の設計を踏襲し、
Foxglove で RAVEN 側のログと並べて見られるようにしてある。

- **生入力をそのまま記録する。** SPI の 20 バイトは base64、vision は protobuf を
  FileDescriptorSet ごと。**仕様が未確定でも今から記録でき、後で再デコードできる。**
- **記録は別 goroutine、ノンブロッキング。** キューが満杯なら捨てて件数を数える。
  **記録が詰まっても推定と制御は絶対に止めない。**
- **フィールド名に単位を埋める**（`wheelFL_rad_s`）。
  このリポジトリは既に `FlWheelSpeedRadS` の中身が m/s という事故を起こしている。

## 4. 計画から変えたところ

### 4.1 符号同定は「1 輪ずつ」ではなく「3 自由度の加振」

計画 §8 は「1 輪ずつ既知方向に動かす」としているが、**これは実行できない**。
SPI の下りは `VelX` / `VelY` / `VelAng` の 3 つしか持たず、車輪個別の指令が存在しない。

代わりに **3 自由度を順に、3 段階の振幅で加振**し、各スロットの
`ω_j = a_j·vx + b_j·vy + c_j·ω` を最小二乗で解く。運動学の基準形と見比べると

```
|(a, b)| = 1/r            → 車輪半径
atan2(a, −b) = A or A+π   → 取付角と符号
c = −s·R/r                → モーメントアーム
```

となり、**符号・ホイール順序・車輪半径・取付角・モーメントアームが同時に出る**。

**限界**: 基準にしているのは「STM へ送った速度指令」なので、同定されるのは
**STM 自身の逆運動学とエンコーダ経路の整合性**であって絶対寸法ではない。
**符号（A-5）とホイール順序（A-4）はこれで確定するが、寸法（A-1〜A-3）の絶対値は確定しない。**
絶対寸法には vision を基準にした同定が要る（`loc_ident -ref vision`、未実装）。

### 4.2 OOSM は retrodiction ではなく「バッファ区間の再フィルタ」

計画 §4.6 は「現在状態を `t_v` へ retrodict し、**全区間の再伝播はしない**」としている。
ここでは**バッファ区間（200 ms / 25 周期）の再フィルタ**を行う。

- 計画が全区間再処理を避ける理由は計算コストだが、25 ステップの再処理を含めて
  **1 周期 5.4 µs** で収まっている。Rock5A で問題にならない。
- 計画自身が引く文献では、retrodiction は全区間再処理に対して共分散が 2〜3% 悪化する
  **近似**である。安く済むなら良いほうを採るのが筋。
- 後退遷移行列を作る必要がなく、実装が単純で誤りが入りにくい。

### 4.3 IEKF（反復更新）は入れていない

計画 §4.4 は vision 観測に IEKF を挙げているが、
**vision の観測モデルは誤差状態に対して厳密に線形である**（`h = [p, theta]` そのもの）。
再線形化する対象が無く、反復しても EKF と数学的に一致する。入れる意味がない。

### 4.4 適応 R・ZUPT / ZARU・オンライン遅延推定も入れていない

いずれも**効果を測れない段階で入れても検証できない**ため。

| | 待っているもの |
| --- | --- |
| 適応 R | 実データ。クランプの上下限が実測なしに決まらない |
| ZUPT / ZARU | 停止判定のしきい値。IMU の短窓分散も使えない |
| オンライン遅延推定 | `v = 0` で不可観測、`v` 一定で位置バイアスと縮退する |

### 4.5 フレーム位相探索が計画から抜けていた

既存実装は 40 バイトのスライディングウィンドウを**総当たりして最後の有効フレームを採る**。
SPI は位相がずれる前提の運用だった。この探索は `stmframe.Decoder.Find` へ移し、
**既存実装と同じ位置を選ぶことをテストで固定**してある。

そのうえで、**窓に 2 フレーム入り得る**。そのとき採用したフレームがどの転送への応答か
一意に決まらず、**時刻が 1 周期（8 ms）ずれ得る**。`/in/spi` の `frameCount` が 2 以上なら
これが起きている。レイテンシ（`tau_stm`）を測るときは必ず見ること。

### 4.6 計画に無かった実装上の問題

1. **パディング 0 がフレーム同期を担っている。** ヘッダ `0xFF` とフッタ `0xAA` だけでは
   2 バイトしか一致を要求できず、20 バイトのずれに対して偽陽性が 1/65536 で起きる。
   8 ms 周期なら数時間に 1 回引く。現行はパディング 7 バイトがこれを 9 バイトへ押し上げている。
   **IMU をバイト 12–18 に載せると 3 バイトへ落ちる。**
   回路担当へ IMU を依頼する際、**CRC を 1 バイト入れてもらう**ことを併せて頼む必要がある。

2. **ロボットが自分のチーム色を知らない。** SSL-Vision は `robots_blue` と `robots_yellow` を
   分けて送り `robot_id` はチーム内採番なので、色が無いと自機を特定できない。
   暫定で `-team` フラグにしたが、**取り違えると相手チームのロボットを自機だと思い込む**。
   恒久的には RAVEN から降ってくるべきで、プロトコル要件書 §1 に `team_color` を足す依頼が要る。

3. **ログのローテーションが未設計。** 試合 10 分あたり数十 MB。容量監視も削除も無い。

## 5. 数字（すべて合成データ）

> **実機の保証ではない。** センサ雑音・遅延の数値は未計測のプレースホルダなので、
> 実測が入れば変わる。**合成データでフィルタを良く見せるためにここを触らないこと。**

### 5.1 vision 生値との比較（片道遅延を較正した場合）

| シナリオ | vision 生値 | 融合値 | 改善 | NEES |
| --- | ---: | ---: | ---: | ---: |
| 直線 2 m/s | 58.2 mm | **5.3 mm** | +91.0% | 1.26 |
| 横移動 1.5 m/s（向き固定） | 43.3 mm | 5.3 mm | +87.8% | 1.26 |
| 円 2 m/s（接線追従） | 58.2 mm | 5.3 mm | +90.9% | 1.26 |
| 円 + 定速スピン | 58.2 mm | 5.3 mm | +90.9% | 1.27 |
| 8 の字 + スピン | 68.5 mm | 5.1 mm | +92.5% | 1.20 |
| 急加速・急停止 | 33.3 mm | 5.2 mm | +84.3% | 1.26 |
| 静止 | 7.2 mm | 5.3 mm | +27.5% | 1.26 |
| **vision 欠落 0.5 s** | 161.6 mm | **5.3 mm** | +96.7% | 1.22 |
| **vision 欠落 2.0 s** | 1123.0 mm | **7.3 mm** | +99.3% | 1.02 |
| スリップバースト | 58.2 mm | 5.7 mm | +90.3% | 1.40 |

計画 §10-4（欠落 0.5 s 後 ≤ 30 mm）と §10-5（欠落 2.0 s 後 ≤ 150 mm）は大きく上回っている。

**NEES の平均が 1.0〜1.4 で、理想の 3.0 より小さい。** フィルタは**保守的**
（共分散を実際の誤差より大きく申告している）。安全な向きだが Q が過大である。
現状は「長期平均をとる推定器」ではなく「**遅延を補償しつつ vision 間を内挿する装置**」に近い。
Q を実測で下げればもっと引き出せる。

**計画 §10-8 の両側 90% は未達**（89.3%）。外れるぶんはすべて弱気側で、
合成データの雑音に Q を合わせ込むのは禁じてあるので**既知の未達として記録してある**。
ハードな合格条件にしてあるのは「過信（Optimistic）が 1% 以下」のほうで、こちらは通っている。

### 5.2 未較正の定数遅延の影響 — 最大の発見

| 速度 | 較正済み | 未較正 | 遅延バイアスの予測値 |
| ---: | ---: | ---: | ---: |
| 0.5 m/s | 6.69 mm | 11.21 mm | 10.00 mm |
| 1.0 m/s | 6.69 mm | 20.53 mm | 20.00 mm |
| 2.0 m/s | 6.69 mm | 40.17 mm | 40.00 mm |
| 3.0 m/s | 6.69 mm | 60.04 mm | 60.00 mm |

**未較正の誤差は、速度 × 定数遅延でほぼ完全に説明できる。**
較正すれば誤差は速度に依存しなくなる（6.69 mm で一定）。
NEES も 1.01 まで健全化する（未較正では 3 m/s で **163**）。

> **速度域で残る誤差は、未較正の定数遅延がその全部である。**
>
> 正体は timesync が原理的に分離できない**最小片方向遅延**。片方向観測だけでは
> 「クロックオフセット」と「最小片方向遅延」を分離できないので、凸包法をどれだけ
> 精密にしても定数分は残る。しかも**これは雑音ではなく系統誤差なので、共分散に一切現れない**。
>
> 計画 §5.3 はこの分離不能性に触れているが、**影響の大きさを書いていない**。
> 実際にはフィルタの洗練より遥かに効く。**計画 §12-D3 は「計測待ち」の 1 項目ではなく、
> §10-1 の達成可否を単独で決める最優先項目である。**
>
> 実測方法: 静止ロボットの vision 座標と既知の真位置を突き合わせるか、
> 既知の一定速度で走らせて進行方向の系統誤差を測る（計画 §10-3）。
> 値は `localization.EstimatorOptions.VisionDelayComp` に入れる。

### 5.3 誤った機体パラメータをフィルタが検出できるか

8 の字 + スピンのシナリオ:

| 設定 | 位置 RMSE | 改善率 | NEES |
| --- | ---: | ---: | ---: |
| 正しい | 4.78 mm | +93.0% | 1.06 |
| **符号反転（A-5）** | **342.3 mm** | **−404%** | **2165** |
| **FL/FR 入れ替わり（A-4）** | 75.4 mm | **−11.1%** | **93.6** |

**符号反転は誰でも気づく。問題は FL/FR 入れ替わりのほう。**
RMSE は vision 生値より 11% 悪い程度で、角度誤差に至ってはほぼ無傷（0.338°）。
実機で見れば「**フィルタを足しても良くならない**」という、
**RAVEN が `EncoderEkfRobotFilter` を不採用にしたときの症状とまったく同じに見える。**

一方 NEES は 1.06 → 93.6 と 90 倍に跳ねる。
**RMSE だけ見ていたら見落とす。NEES を見れば必ず捕まる。**
計画 §9「共分散の正しさも測る」を機能要件にした理由の実証になっている。

車輪の解釈だけを見た場合（フィルタを通す前）の誤差は次の通りで、
**FL/FR 入れ替わりは角速度には出ず速度にだけ出る、モーメントアームの誤りは角速度にだけ出る。
片方だけ見ていると見落とす。**

| 設定 | 速度誤差 | 角速度誤差 |
| --- | ---: | ---: |
| 正しい | 0.0002 m/s | 0.0017 rad/s |
| 符号反転（A-5） | 6.66 m/s | 2.40 rad/s |
| FL/FR 入れ替わり（A-4） | 3.82 m/s | 0.0017 rad/s |
| 車輪半径 27 vs 30 mm（A-1） | 0.33 m/s | 0.12 rad/s |
| モーメントアーム 90 vs 75 mm（A-2） | 0.0002 m/s | 0.20 rad/s |

### 5.4 スリップ状態の既定値（掃引で決定）

`τ_s` × `Q_s` を 12 通り、4 シナリオで比較した（`TestSlipParameterSweep`）。
判断基準は **RMSE ではなく過信（NEES が上側へ外れるサンプル数）**。
位置制御は共分散を見てゲインを決めるので、ずれているのに自信満々な状態が一番危ない。

| 設定 | スリップ無しの RMSE | 定常スリップ + 欠落の NEES | 過信サンプル |
| --- | ---: | ---: | ---: |
| OFF | **2.65 mm** | **174.8** | **1126 / 1126** |
| τ 0.05 / Q 1.0 | 5.74 mm | 4.57 | 174 |
| **τ 0.10 / Q 1.0（採用）** | 6.85 mm | 1.88 | **0** |
| τ 0.30 / Q 1.0 | 7.87 mm | 1.04 | 0 |

**スリップを切ると、124 mm ずれながら共分散は締まったまま**という最悪の振る舞いになる。
`τ_s = 0.1`（計画 §4.3 の既定値と一致）、`Q_s = 1.0` が、
スリップのある全シナリオで過信ゼロを達成する最も安価な設定だった。

### 6.1 実機が使えるようになったら（最優先）

```
# 周囲を空ける。約 40 秒間ロボットが自走する。非常停止は効いたまま。
racoon-pi2 -loclog /var/log/racoon -team blue -locident
```

| --- | --- | --- |
| **符号規約** | A-5 | 逆なら融合が逆効果になる。RAVEN 失敗の最有力候補 |
| **ホイール順序** | A-4 | 左右が入れ替わる。**RMSE には出ない**（§5.3） |
| 速度スケール | A-1〜A-3 | 相対値のみ。絶対値は vision 基準の同定が要る |

**この 8 つが埋まるまで、精度目標（計画 §10）の達成可否は語れない。**

### 6.2 実機なしで進められること（優先度順）

1. **`cmd/loc_replay`** — 実機ログ（MCAP）を推定器へ流し直し、パラメータを掃引する道具。
   **これが無いと P1 で録ったログをフィルタの改善に使えない。**
   `internal/loclog` の Reader と `internal/locsim` の評価はもう揃っているので、
   繋ぎ込みが中心になる。計画 §6.3 の「同じ MCAP を流せばビット単位で同じ推定結果」も
   ここで担保する。

2. **RTS スムーザ** — 実機には真値が無い。平滑化結果を疑似真値として使う（計画 §8）。
   オフラインは未来の観測も使えるため、原理的にオンライン推定より必ず良い。
   **これが無いと実機で精度を測れない。**

3. **`loc_ident -ref vision`** — vision を基準にした同定で、寸法の**絶対値**を出す。
   timesync が入ったので前提は揃っている。vision の数値微分と遅延補償の扱いが要る。

4. **Q の感度解析** — 現状 NEES 平均が 1.2 で保守的（§5.1）。
   Q を下げるとどこまで良くなり、どこで過信に転ぶかを合成データで地図にしておく。
   **合成データに合わせ込むのではなく、実測値が来たときに当てはめる先を用意する。**

## 7. コードを触るときの約束

1. **`localization` / `timesync` / `stmframe` / `loclog` / `locadapter` / `locsim` に
   ビルドタグを付けない。** 開発 PC でテストが回らなくなる。

2. **`localization` と `timesync` から `time.Now()` を呼ばない。** 時刻は `Stamp` で引数として渡す。
   同じ MCAP から同じ出力が出ることが、オフラインチューニングと回帰テストの前提。

3. **SPI のホットパスで新しくアロケートしない。** 6 本のテストが 0 アロケーションを固定している。
   `any` へのボックス化ひとつでも落ちる。

4. **記録が詰まっても推定と制御を止めない。** 捨てて件数を数える。

5. **ログのフィールド名に単位を書く**（`wheelFL_rad_s`）。
   このリポジトリは既に `FlWheelSpeedRadS` の中身が m/s という事故を起こしている。

6. **`state.FlWheelSpeedRadS` を参照しない。** 名前と単位が一致していない。

7. **合成データに Q / R を合わせ込まない。** 合成データの雑音は実機の雑音ではない。
   合わせ込むと後で剥がせない嘘になる。未計測の値には「**未計測**」と書いてある。

8. **推定の良し悪しは RMSE と NEES を必ず両方見る。**
   NEES が跳ねているのに RMSE が普通なら、フィルタではなくパラメータを疑う（§5.3）。

## 8. 経緯のメモ

**「符号が確定するまでフィルタを書かない」は撤回した。**

この文書の初版はそう書いていたが、誤りだった。
符号もホイール順序も `GeometryConfig` の値でしかなく、行列 `M` の行の符号を変えたり
入れ替えたりするだけで、**ヤコビアンの形も状態次元も更新式も変わらない**。
正しくは「確定するまで**チューニングと評価**をしないこと」である。

RAVEN の EKF の失敗は「間違ったパラメータでフィルタを書いた」ことではなく、
**間違ったパラメータのまま効果を測ろうとして切り分けられなかった**ことである。
禁じるべきは執筆ではなく評価だった。

そのうえで、次の 3 つを守って進めた。

- `eskf.go` より先に検証ハーネスを書いた（RAVEN の教訓は順序ではなく**測定可能性**のほう）
- 符号を反転させたら精度が悪化することをテストで固定した（§5.3）
- Q / R は「未チューニング」と明示した固定値で止めた
