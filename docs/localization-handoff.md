### 3.2 状態の持ち方

```
公称状態   theta (ワールド姿勢), p (ワールド位置), V (ワールド速度),
           omega (ヨーレート), s (ロボット系スリップ速度)
誤差状態   [dPhi, dP(2), dV(2), dOmega, dS(2)]  = 8 次元
```

計画 §4.2 の 10 次元から **ジャイロバイアス `b_omega` を落とし、`omega` を入力ではなく
状態に昇格させてある**。IMU が存在しないので、ジャイロを予測の入力にできないため。
IMU が載ったら `AddImu` の中身を書いて元の設計へ戻せるよう、入り口だけ先に決めてある。

**速度をワールド系で持つのが部分不変（PIEKF）の肝である。** 位置の誤差伝播が

```
d(dP)/dt = dV
```

となり、**推定値（theta や V）に一切依存しない**。ロボット系で持つと
`d(dP)/dt = R(theta)·dV + J·R(theta)·V·dPhi` となって推定軌道に依存し、
共分散が推定の出来不出来に引きずられる。位置は誤差が一番育つ経路なので、
ここを推定非依存にすることが一貫性に効く。

姿勢は SO(2) なので**左不変と右不変が一致する**（2 次元の回転は可換）。
誤差の注入が単なる加算 + 折り返しで済み、**共分散のリセット変換も恒等になる**。
3 次元なら `J = I − 0.5·[dPhi]×` を掛ける必要がある。

## 4. 計画から意図的に変えた点

### 4.1 符号同定の方法（§8）

計画は「**1 輪ずつ既知方向に動かす**」としているが、**これは実行できない**。
SPI の下りは `VelX` / `VelY` / `VelAng` の 3 つしか持たず、車輪個別の指令が存在しない。
STM 側が逆運動学で 4 輪へ配分するので、1 輪だけ回す経路が無い。

代わりに **3 自由度を順に、3 段階の振幅で加振**し、各スロットの

```
ω_j = a_j·vx + b_j·vy + c_j·ω
```

を最小二乗で解く方式にした（`localization.Identify`）。運動学の基準形と見比べると

```
|(a, b)| = 1/r            → 車輪半径
atan2(a, −b) = A or A+π   → 取付角と符号
c = −s·R/r                → モーメントアーム
```

となり、**符号・ホイール順序・車輪半径・取付角・モーメントアームが同時に出る。**

**限界（重要）**: 基準にしているのは「STM へ送った速度指令」なので、同定されるのは
**STM 自身の逆運動学とエンコーダ経路の整合性**であって絶対寸法ではない。
**符号（A-5）とホイール順序（A-4）はこれで確定するが、寸法（A-1〜A-3）の絶対値は確定しない。**
STM 側の運動学パラメータが間違っていれば、その誤差ごと吸収する。
絶対寸法には vision を基準にした同定が要り、それは **P2 の後**でないと成立しない。
`loc_ident -ref vision` は現状そう明示してエラーを返す。

### 4.2 timesync（P2）— 実装済み

> **2026-09-13 追記: P2 は実装した。** 初版は「P1 では timesync を使わない」と書いていたが、
> 凸包法は合成データだけで開発・検証できるため先に入れた。

`internal/timesync/convexhull.go`。点群 `(t_capture, t_arrive − t_capture)` の**下側凸包**を取り、
重心の x を跨ぐ辺の傾きをスキュー、切片をオフセットとする。

実装上の要点:

- **LP を解いていない。** 目的は `Σ(y_i − (a·x_i + b))` の最小化・制約は `a·x_i + b ≤ y_i` で、
  目的関数が `a·Σx + n·b` なので「**重心の x での直線の値の最大化**」と等価になる。
  その最適解は**重心の x を跨ぐ下側凸包の辺そのもの**である。O(n log n) で数値的にも安定する。
- **数値精度**: `t_capture` は vision PC の起動からの秒なので ns にすると 1e14 になる。
  最初の観測を epoch として差分に直してから当てはめる。
- **`OffsetNs` は絶対時刻ゼロ点での切片ではない。** それはスキューに掛かって数秒規模になり
  物理的な意味を持たない。報告しているのは**その観測を写すのに足した量**
  ＝現時点の「クロックオフセット + 最小片方向遅延」で、§5.5 が監視したいのはこちら。
- **凸包の組み直しは 500 ms ごと。** クロックのドリフトは分オーダーなので毎パケットは要らない。
  経過は到着 `Stamp` で測るので `time.Now()` は呼ばない。

**`camera_id` ごとに独立した推定器を持つ**（`MultiSync`）。これは P0 で切ったインタフェースの
**設計ミスを直したもの**で、初版の `Sync` はカメラを区別できなかった。カメラごとに露光から
送信までの処理遅延が違うので、混ぜると凸包の下端が一番速いカメラに引きずられる。

合成データでの実測値（`go test ./internal/timesync/ ./internal/locadapter/ -v`）:

| 項目 | 結果 | 目標（計画 §10-10） |
| --- | --- | --- |
| スキュー残差（0 / ±50 / ±120 ppm） | **< 10 ppm** | ≤ 10 ppm |
| 写像誤差 RMS | **561 ns**（最大 1.0 µs） | ≤ 2 ms |
| バースト遅延下のスキュー誤差 | **凸包 0.00 ppm** / 最小二乗 67.73 ppm | — |
| 受信器込みの写像誤差 RMS | **5.5 µs**（到着時刻そのままなら 5.27 ms） | — |

バースト下で最小二乗が 67 ppm 外すのに凸包が 0 ppm なのが、
計画 §13「凸包法（EMA を使わない）」の根拠そのものである。これはテストで固定してある。

**残る系統誤差**: 最小片方向遅延の定数分は片方向観測だけでは原理的に分離できない。
オフラインで実測して定数として持つ必要がある（計画 §5.3）。

### 4.3 OOSM は retrodiction ではなく「バッファ区間の再フィルタ」にした

計画 §4.6 は「現在状態を `t_v` へ retrodict し、補正を現在時刻へ伝播する。
**全区間の再伝播はしない**」としている。ここでは**バッファ区間（200 ms / 25 周期）の
再フィルタ**を行う。理由:

- 計画が全区間再処理を避ける理由は計算コストだが、25 ステップの再処理は 8×8 の
  行列演算 25 回。実測で **1 周期 5.4 µs**（vision 込み）なので問題にならない。
- 計画自身が引く文献では、retrodiction は全区間再処理に対して共分散が 2〜3% 悪化する
  **近似**である。安く済むなら良いほうを採るのが筋。
- 後退遷移行列を作る必要がなく、実装が単純で誤りが入りにくい。

## 5. 実装中に見つかった、計画に無かった問題

詳細は [`localization-p1-runbook.md`](./localization-p1-runbook.md) §4。要点だけ:

1. **フレーム位相探索が計画から抜けていた。** 既存実装は 40 バイト窓を総当たりしていた。
   `stmframe.Decoder.Find` へ移し、既存実装と同じ位置を選ぶことをテストで固定した。
   さらに**窓に 2 フレーム入り得る**ので、`/in/spi` の `frameCount` が 2 以上なら
   時刻が 1 周期（8 ms）ずれ得る。`τ_stm` を測るときに効く。

2. **パディング 0 がフレーム同期の判別力を担っている**（9 バイト → IMU を載せると 3 バイト）。
   回路担当への依頼（§12-B3）に **CRC 1 バイト**を追加する必要がある。

3. **ロボットが自分のチーム色を知らない。** SSL-Vision は青黄を分けて送り `robot_id` はチーム内採番なので、
   色が無いと自機を特定できない。暫定で `-team` フラグにしたが、
   **取り違えると相手チームのロボットを自機だと思い込む**。
   プロトコル要件書 §1 に `team_color` を足す依頼が要る。

4. **ログのローテーションが未設計。** 試合 10 分あたり数十 MB。容量監視も削除も無い。

5. **未較正の vision 定数遅延が、速度域の誤差の「ほぼ全部」である。**（§6.3.2 で詳述）
   timesync が原理的に分離できない最小片方向遅延は、**雑音ではなく系統誤差**なので
   共分散に一切現れない。放置すると誤差が速度に比例して増え、NEES が破綻する。
   計画は §5.3 でこれに触れているが、**影響の大きさが書かれていない**。
   実測（D-3）は「あると良い」ではなく**最優先項目**である。

6. **ホイール順序の取り違え（A-4）は RMSE にほとんど出ず、NEES にだけ大きく出る。**
   これはおそらく **RAVEN の「効果が測れなかった」の症状そのもの**である。（§6.3.2）

### 6.2 実機がなくても進められること（2026-09-13 合意の方針）

> **この文書の初版は「A-4 / A-5 が確定するまでフィルタを書き始めないこと」と書いていた。
> それは誤りだったので撤回する。** 正しくは「**確定するまでチューニングと評価をしないこと**」である。

**符号もホイール順序も、フィルタの構造に一切影響しない。**
車輪観測モデルは `h(x) = M·v_body + s` で、`M` は `GeometryConfig` から組み立てられる。
符号反転は `M` の行の符号が変わるだけ、ホイール順序の入れ替わりは行が入れ替わるだけで、
**ヤコビアンの形も状態次元も更新式も変わらない。** P1 の結果は JSON を差し替えれば入る。

RAVEN の EKF の失敗は「間違ったパラメータでフィルタを書いた」ことではなく、
**間違ったパラメータのまま効果を測ろうとして切り分けられなかった**ことである。
禁じるべきは執筆ではなく評価である。

### 6.3 決めた実装順序

**P2（timesync）→ 最小のフィルタ → P1 待ちの評価**

**1. P2 を先にする。** 計画 §5 の言う通り「この系の精度を決めるのはフィルタの洗練ではなく、
どの値がいつの瞬間のものか」だからである。凸包法は合成データ（既知スキュー +50 ppm、
バースト遅延、AP ローミング相当のステップ）で完全に開発・検証でき、**P1 待ちがゼロ**。
vision 観測の更新を書くときに時刻写像が揃っている状態になる。

**2. フィルタは最小構成で止める。** 予測 ＋ 車輪観測 ＋ **固定 R** の vision 観測まで。
適応 R・オンライン遅延推定・反復更新（IEKF）は**効果を測れない段階で入れても検証できない**。
計画 §4 は全部載せだが、実データが無いうちに作ると過剰実装になる。

**3. 守る条件（この 3 つを外さないこと）**

- **`eskf.go` より先に合成データの検証ハーネスを書く。**
  円・8 の字・急加減速の真値を生成し、雑音・遅延・欠落を注入して
  「vision 生値 vs 融合値の RMSE」を出す土台。これを後回しにすると、
  また「効果が測れない」状態でコードだけ増える。**RAVEN の教訓は順序ではなく測定可能性のほう。**
- **符号を反転させたら精度が悪化することをテストで固定する。**
  A-5 に直接効く。もし**フィルタが符号の誤りを検出できないなら、それ自体が重大な発見**である
  （＝実機で符号が逆でも気づけない）。イノベーションの系統的な偏りとして必ず出るはずで、
  出ないなら観測モデルの設計を疑うべき。
- **Q / R は「未チューニング」と明示した固定値で止める。**
  合成データの雑音は実機の雑音ではない。ここを合成データに合わせ込むと、後で剥がせない嘘になる。

### 6.3.1 検証ハーネス（`internal/locsim`）— 実装済み

`eskf.go` より先に書くと決めた土台。**フィルタはまだ無いが、フィルタを測る道具はできている。**

| ファイル | 内容 |
| --- | --- |
| `trajectory.go` | 解析軌道。静止 / 等加速度直線 / 円 / 8 の字 / 急加減速 |
| `sensors.go` | 真値から車輪・vision を合成。雑音・量子化・遅延・欠落・スリップを注入 |
| `metrics.go` | RMSE、**vision 生値との比較**、NEES による一貫性検定 |

**向きと進行方向を分離してある**（`HeadingFixed` / `HeadingSpin` / `HeadingTangent`）。
接線追従だけで検証すると機体系の `vy` が常に 0 になり、**横方向の可観測性を一切試さないまま
「動いた」ことになってしまう**。SSL のロボットは全方向移動なので、固定向き・定速スピンを既定に使う。

真値そのものが間違っていたら下流が全部無意味になるので、**速度が位置の微分か、
ヨーレートが角度の微分か**を全軌道 × 全向きモードで数値微分と突き合わせてある。

#### 誤った機体パラメータの検出可能性（実測値）

真の幾何で合成した車輪データを、**誤った設定**で読み戻したときの body 速度の復元誤差:

| 設定 | 速度誤差 | 角速度誤差 |
| --- | ---: | ---: |
| 正しい | 0.0002 m/s | 0.0017 rad/s |
| **符号反転（A-5）** | **6.66 m/s** | **2.40 rad/s** |
| **FL/FR 入れ替わり（A-4）** | **3.82 m/s** | 0.0017 rad/s |
| 車輪半径 27 vs 30 mm（A-1） | 0.33 m/s | 0.12 rad/s |
| モーメントアーム 90 vs 75 mm（A-2） | 0.0002 m/s | 0.20 rad/s |

**4 つの間違いはすべて桁違いに大きな誤差として現れる。** つまり実機で符号やホイール順序が
違っていれば、車輪の解釈の段階で必ず見える。§6.3 の守る条件 2 はこの性質の上に立っている。

> FL/FR 入れ替わりは角速度には出ず速度にだけ出る、モーメントアームの誤りは
> 角速度にだけ出る、という違いに注意。**片方だけ見ていると見落とす。**

#### 比較の基準線（実測値）

2 m/s 直線走行・vision 遅延 20 ms・雑音 5 mm のとき、
**vision 生値をそのまま保持した場合の位置 RMSE は 57.3 mm**（最大 111.6 mm）。
これがフィルタの越えるべき棒である。計画 §10-2（50% 削減）なら 28.6 mm 以下、
§10-1（RMSE 10 mm）なら 10 mm 以下。

#### NEES の検定が機能していることの確認

既知の共分散から誤差を引いた合成推定に対して:

| 申告した共分散 | 平均 NEES（理想 3.0） | 95% 区間内 | 判定 |
| --- | ---: | ---: | --- |
| 正直 | **3.04** | **94.9%** | — |
| 3 倍過信（分散 1/9） | 27.28 | 21.3% | Optimistic 5894 / Pessimistic 6 |
| 3 倍弱気（分散 9 倍） | 0.33 | 57.9% | Optimistic 0 / Pessimistic 3156 |

理論値通りに動いている。**過信（Optimistic）を捕まえられることが重要**で、
位置制御が共分散を見てゲインを決める以上、この向きの誤りが一番危ない。

> **センサ設定の数値はすべて未計測のプレースホルダである**（雑音 5 mm、遅延 20 ms 等）。
> 実測は P1 の D-1〜D-7 で埋まる。**合成データでフィルタを良く見せるためにここを触らないこと。**

### 6.3.2 PIEKF の実測結果（合成データ）

**すべて合成データの値であり、実機の保証ではない。** センサ雑音・遅延の数値は
未計測のプレースホルダなので、実測が入れば変わる。

#### vision 生値との比較（片道遅延を較正した場合）

| シナリオ | vision 生値 | 融合値 | 改善 | NEES |
| --- | ---: | ---: | ---: | ---: |
| 直線 2 m/s | 58.2 mm | **5.3 mm** | +91.0% | 1.26 |
| 横移動 1.5 m/s（向き固定） | 43.3 mm | 5.3 mm | +87.8% | 1.26 |
| 円 2 m/s（接線追従） | 58.2 mm | 5.3 mm | +90.9% | 1.26 |
| 円 + 定速スピン | 58.2 mm | 5.3 mm | +90.9% | 1.27 |
| 8 の字 + スピン | 68.5 mm | 5.1 mm | +92.5% | 1.20 |
| 急加速・急停止 | 33.3 mm | 5.2 mm | +84.3% | 1.26 |
| 静止 | 7.2 mm | 5.3 mm | +27.5% | 1.26 |
| **vision 欠落 0.5 s** | 161.6 mm | **5.3 mm** | +96.7% | 1.22 |
| **vision 欠落 2.0 s** | 1123.0 mm | **7.3 mm** | +99.3% | 1.02 |
| スリップバースト | 58.2 mm | 5.7 mm | +90.3% | 1.40 |

計画 §10-4（欠落 0.5 s 後 ≤ 30 mm）と §10-5（欠落 2.0 s 後 ≤ 150 mm）は
合成データ上では大きく上回っている。

> **NEES の平均が 1.0〜1.4 で、理想の 3.0 より小さい。** フィルタは**保守的**
> （共分散を実際の誤差より大きく申告している）。安全な向きだが、Q が過大である。
> 合成データに Q を合わせ込むのは禁じてあるので、**実測待ち**。
> 現状フィルタは「長期平均をとる推定器」ではなく「**遅延を補償しつつ vision 間を
> 内挿する装置**」に近い挙動をしている。Q を実測で下げればもっと引き出せる。

#### 未較正の定数遅延の影響 — 最大の発見

| 速度 | 較正済み | 未較正 | 遅延バイアスの予測値 |
| ---: | ---: | ---: | ---: |
| 0.5 m/s | 6.69 mm | 11.21 mm | 10.00 mm |
| 1.0 m/s | 6.69 mm | 20.53 mm | 20.00 mm |
| 2.0 m/s | 6.69 mm | 40.17 mm | 40.00 mm |
| 3.0 m/s | 6.69 mm | 60.04 mm | 60.00 mm |

**未較正の誤差は、速度 × 定数遅延でほぼ完全に説明できる。** 較正すれば誤差は
速度に依存しなくなる（6.69 mm で一定）。NEES も 1.01 まで健全化する
（未較正では 3 m/s で **163**）。

> **つまり、速度域で残る誤差は未較正の定数遅延がその全部である。**
> フィルタの洗練ではなく、**`τ_net` の定数分を実測すること**が精度を決める。
> 計画 §5 の「この系の精度を決めるのはフィルタの洗練ではなく、どの値が
> いつの瞬間のものか」が、数字で裏付けられた形になる。
>
> 実測方法: 静止したロボットで vision 座標と既知の真位置を突き合わせるか、
> 既知の一定速度で走らせて進行方向の系統誤差を測る（計画 §10-3）。
> 値は `EstimatorOptions.VisionDelayComp` に入れる。

#### 誤った機体パラメータをフィルタが検出できるか

8 の字 + スピンのシナリオ:

| 設定 | 位置 RMSE | 改善率 | NEES |
| --- | ---: | ---: | ---: |
| 正しい | 4.78 mm | +93.0% | 1.06 |
| **符号反転（A-5）** | **342.3 mm** | **−404%** | **2165** |
| **FL/FR 入れ替わり（A-4）** | 75.4 mm | **−11.1%** | **93.6** |

**符号反転は誰でも気づく。問題は FL/FR 入れ替わりのほう。**
RMSE は vision 生値より 11% 悪い程度で、角度誤差に至ってはほぼ無傷（0.338°）。
実機で見れば「**フィルタを足しても良くならない**」という、
**RAVEN が報告した症状とまったく同じに見える。**

一方 NEES は 1.06 → 93.6 と 90 倍に跳ねる。
**RMSE だけ見ていたら見落とす。NEES を見れば必ず捕まる。**
これが計画 §9「共分散の正しさも測る」を機能要件にした理由の実証になっている。

#### スリップ状態の既定値（掃引で決定）

`τ_s` × `Q_s` を 12 通り、4 シナリオで比較した（`TestSlipParameterSweep`）。
判断基準は **RMSE ではなく過信（NEES が上側へ外れるサンプル数）**。
位置制御は共分散を見てゲインを決めるので、ずれているのに自信満々な状態が一番危ない。

| 設定 | スリップ無しの RMSE | 定常スリップ + 欠落の NEES | 過信サンプル |
| --- | ---: | ---: | ---: |
| OFF | **2.65 mm** | **174.8** | **1126 / 1126** |
| τ 0.05 / Q 1.0 | 5.74 mm | 4.57 | 174 |
| **τ 0.10 / Q 1.0（採用）** | 6.85 mm | 1.88 | **0** |
| τ 0.30 / Q 1.0 | 7.87 mm | 1.04 | 0 |

**スリップを切ると、124 mm ずれながら共分散は締まったまま**という最悪の振る舞いになる。
`τ_s = 0.1`（計画 §4.3 の既定値と一致）、`Q_s = 1.0` が、
スリップのある全シナリオで過信ゼロを達成する最も安価な設定だった。

## 7. コードを触るときの約束

1. **`localization` / `timesync` / `stmframe` / `loclog` / `locadapter` にビルドタグを付けない。**
   開発 PC でテストが回らなくなる。
2. **`localization` と `timesync` から `time.Now()` を呼ばない。** 時刻は `Stamp` で引数として渡す。
   同じ MCAP から同じ出力が出ることが、オフラインチューニングと回帰テストの前提（計画 §7.4）。
3. **SPI のホットパスで新しくアロケートしない。** `TestSPIRecorderDoesNotAllocate` など
   3 本のテストが 0 アロケーションを固定している。`any` へのボックス化でも落ちる。
4. **記録が詰まっても推定と制御を止めない。** 捨てて件数を数える。
5. **ログのフィールド名に単位を書く**（`wheelFL_rad_s`）。
   このリポジトリは既に `FlWheelSpeedRadS` の中身が m/s という事故を起こしている。
6. **`state.FlWheelSpeedRadS` を参照しない。** 名前と単位が一致していない。
