# P1 計測基盤 — 実行手順

[`self-localization-plan.md`](./self-localization-plan.md) の **P0 / P1** の実装ぶんの使い方。
フィルタ本体 (P3 以降) はまだ無い。ここで取るのは**以降の判断の根拠になる事実**である。

## 1. ログを取る

```
racoon-pi2 -loclog /var/log/racoon -team blue
```

| フラグ | 意味 |
| --- | --- |
| `-loclog DIR` | 計測ログ (MCAP) の出力先。**指定しなければ何も記録せず、従来と完全に同じ動作になる** |
| `-team blue\|yellow` | 自機の色。**SSL-Vision から自機を特定するのに必須** (§4 参照) |
| `-locprofile NAME` | STM フレームのプロファイル。既定 `rock5a-v1` (IMU なし)。IMU が載ったら `rock5a-v2-imu` |
| `-visionaddr ADDR` | SSL-Vision のマルチキャスト。既定 `224.5.23.2:10694` |
| `-visioniface NIC` | 受信に使う NIC。**Rock5A は有線と無線を両方持つので、取り違えると「一切来ない」形で静かに失敗する** |
| `-locident` | 機体パラメータ同定の加振を実行する。**ロボットが自走する** |

出力は `DIR/racoon-loc-<日時>-id<N>.mcap`。Foxglove でそのまま開ける。

### 記録されるトピック

| トピック | 内容 |
| --- | --- |
| `/in/spi` | **SPI の生フレーム 20 バイト** (tx / rx を base64)、転送時刻、実測 dt、採用したフレーム位置 |
| `/in/vision` | `SSL_WrapperPacket` の生 protobuf。FileDescriptorSet 同梱なので Foxglove が単体でデコードできる |
| `/in/vision_meta` | `t_capture` / `t_sent` / 受信時刻 / **frame_number の欠番** / 自機の観測値 |
| `/sensors/wheel` | デコード後の 4 輪角速度と生値、バッテリ電圧 |
| `/sensors/imu` | ジャイロ・加速度。**STM が送っていないので現状は空** |
| `/out/command` | STM へ送った指令 (mm/s, mrad/s) |
| `/est/timing` | 実測 dt |
| `/recorder/status` | 記録自体の健全性。**捨てた件数** |

**記録が詰まっても推定と制御は絶対に止まらない。** キューが満杯なら捨てて件数を数える。

## 2. 符号・ホイール順序・寸法を確定させる (最優先)

計画 §12-A の 5 項目 (A-1 車輪半径 / A-2 モーメントアーム / A-3 取付角 / **A-4 ホイール順序** / **A-5 符号規約**) を実測で潰す。
A-4 と A-5 は「RAVEN の EKF は効果が測れなかった」の最有力の原因候補である。

### なぜ 1 輪ずつ回さないのか

**SPI の下りには車輪個別の指令が存在しない。** `VelX` / `VelY` / `VelAng` の 3 つだけで、
STM 側が逆運動学で 4 輪へ配分する。計画 §8 の「1 輪ずつ既知方向に動かす」は現行プロトコルでは実行できない。

代わりに **3 自由度を順に、複数の振幅で加振**し、4 輪の応答行列から解く。各スロット `j` について

```
omega_j = a_j*vx + b_j*vy + c_j*omega
```

を最小二乗で求めると、運動学の基準形と見比べて

```
|(a, b)| = 1/r          -> 車輪半径
atan2(a, -b) = A or A+pi -> 取付角と符号
c = -s*R/r               -> モーメントアーム
```

となり、**符号・ホイール順序・車輪半径・取付角・モーメントアームがすべて同時に出る。**

### 手順

```
# 周囲を空ける。非常停止は効いたままである。
racoon-pi2 -loclog /var/log/racoon -team blue -locident

# 約 40 秒で終わる。終わったらログを回収して
loc_ident -log racoon-loc-20260913-101500-id3.mcap -v

# 結果を設定として書き出す
loc_ident -log ... -out geometry.json
```

`loc_ident` は「4 候補のどれに最も近いか」と、符号反転・ホイール入れ替わりが**実際に起きているか**を判定して出す。

### この同定で分かること・分からないこと

基準に使っているのは **RAVEN への指令ではなく、STM へ送った速度指令**である。したがって同定されるのは
**「STM 自身の逆運動学とエンコーダ経路の整合性」**であって、絶対的な機体寸法ではない。

- **符号 (A-5) とホイール順序 (A-4) はこれで確定する。** ここが目的である。
- **寸法 (A-1〜A-3) の絶対値は確定しない。** STM 側の運動学パラメータが間違っていれば、その誤差ごと吸収する。
  絶対寸法には vision を基準にした同定 (`-ref vision`) が要り、それは **P2 (timesync) の後**でないと成立しない。

## 3. マルチキャストの欠落率とジッタ

- **欠落率**: `/in/vision_meta` の `frameGap` / `lostFrames` / `totalFrames`。`camera_id` ごとに独立に追う。
  順序逆転と重複は `lostFrames` に混ぜず別に数える。
- **vision の処理遅延**: `/in/vision_meta` の `processing_s` = `t_sent - t_capture`。
  **同一クロック内の差なので、クロック同期なしで正確に測れる。**
- **SPI のジッタ**: `/in/spi` の `dt_ns`。公称 8 ms との差が GC とスケジューリングの影響。
  `time.Ticker` は使わず、`conn.Tx()` の**直前・直後の中点**を転送時刻にしている。

## 4. 実装時に判明した、計画に無かったこと

### 4.1 フレーム位相探索が計画から抜けていた

既存実装は 40 バイトのスライディングウィンドウを**総当たりして最後の有効フレームを採る**。
SPI は位相がずれる前提の運用だった。この探索は `stmframe.Decoder.Find` へ移し、
既存実装と**同じ位置を選ぶことをテストで固定**してある。

そのうえで、**窓に 2 フレーム入り得る**。そのとき採用したフレームがどの転送への応答か一意に決まらず、
**時刻が 1 周期 (8 ms) ずれ得る**。`/in/spi` の `frameCount` が 2 以上ならこれが起きている。
レイテンシ (計画 §5.4 の `tau_stm`) を測るときは必ず見ること。

### 4.2 パディング 0 がフレーム同期を担っている

ヘッダ `0xFF` とフッタ `0xAA` だけでは 2 バイトしか一致を要求できず、20 バイトのずれに対して
偽陽性が 1/65536 で起きる。8 ms 周期なら数時間に 1 回は引く計算になる。
現行フレームは**パディング 7 バイトがこれを 9 バイトへ押し上げている**。

**IMU をバイト 12–18 に載せると、この判別力が 3 バイトへ落ちる。**
`Profile.SyncStrength()` がこの値を返し、テストで両プロファイルの差を固定してある。
計画 §12-B3 で回路担当へ IMU のバイト配置を依頼する際、**CRC を 1 バイト入れてもらう**ことを併せて頼む必要がある。

### 4.3 ロボットは自分のチーム色を知らない

SSL-Vision は `robots_blue` と `robots_yellow` を分けて送り、`robot_id` はチーム内で採番される。
**色が分からないと自機を特定できない**が、現在のコードベースに色を知る経路が一切無い。

暫定で起動フラグ `-team` にしてある。**取り違えると相手チームのロボットを自機だと思い込む**ので、
恒久的には RAVEN から降ってくるべきである。
[`robot-command-protocol-requirements.md`](./robot-command-protocol-requirements.md) の §1 へ
`team_color` を足すよう通信担当へ依頼すること。

### 4.4 ログのローテーションが未設計

125 Hz の SPI と 60 Hz の vision を記録すると、**試合 10 分あたり数十 MB** になる。
現状は起動ごとに新しいファイルを作るだけで、古いファイルの削除も容量の監視も無い。
Rock5A の eMMC / SD の空き容量を運用で見ること。
