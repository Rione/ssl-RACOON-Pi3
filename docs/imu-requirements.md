# IMU から欲しいデータ (STM → Pi)

**宛先**: ロボットのハード・STM のファームの担当
**書いた理由**: Rock5A 側で自己位置推定と軌道の追従を動かすのに IMU を使いたい。受け渡しの形を決めたい
**最終更新**: 2026-09-23

Pi 側は SPI の受け口 (`internal/stmframe/profiles/rock5a-v2-imu.json`) を先に用意してあります。
バイトの配置と倍率はこの表のとおりです。**変えたいところがあれば言ってください。JSON を 1 行直すだけで合わせられます。**

---

## 1. 欲しい信号 (優先順)

| # | 信号 | 要る度合い | 何に使うか |
|---|---|---|---|
| 1 | **ヨー方向の角速度 (ジャイロ Z)** | **必須** | 向きと角速度の推定。今は指令が効くまで約 90 ms 遅れるので、その間を埋める。向きのぶれ (実測で最大 7〜29°) を抑える内側のループにも使う |
| 2 | **機体の加速度 X・Y** | あると良い | vision が途切れた間の速度の保持。「車輪は回っているのに機体が加速していない」= 滑りの検出 |
| 3 | 温度 | あると良い | ジャイロのバイアスの温度ドリフトの補正 (1 バイトで十分) |
| 4 | ジャイロ X・Y、加速度 Z | 今は要らない | 平面の運動しか扱わないため |

## 2. 形式: **生の値が欲しい (積分済みの姿勢角は不可)**

- **積分して出した「今の向き (角度)」は要りません**。それだけだと、こちらでバイアスを推定できず、vision と正しく混ぜられません
- ジャイロは**角速度**、加速度計は**加速度**そのままでください
- 工場・起動時の固定オフセットを 1 回引くのは歓迎です。ただし**その後は触らないでください** (走行中にゼロ点を動かされると、こちらの推定と二重になります)
- 単位・倍率は決めてもらって構いません。**その値を教えてください** (今の想定は下の表)

| 信号 | 今の想定の型 | 倍率 | 範囲 |
|---|---|---|---|
| gyroZ | int16 (リトルエンディアン) | 0.000133231 rad/s / LSB | ±250 deg/s |
| accelX, accelY | int16 (リトルエンディアン) | 0.00059855 m/s² / LSB | ±2 g |

**範囲は見直したいです。**
- ジャイロ ±250 deg/s は、試合の急な旋回で飽和する可能性があります (±500〜1000 deg/s を推奨)
- 加速度 ±2 g は、ボールを蹴る衝撃や接触で飽和します (±4〜8 g を推奨)
- どちらも int16 のままで足ります。倍率だけ変えてもらえれば大丈夫です

## 3. 出し方 (サンプリングと時刻)

- SPI は 125 Hz (8 ms) です。**1 フレームに 1 組**入れてください
- **第 1 希望: 8 ms の間の積分値** (ジャイロなら角度の増分 Δθ [rad]、加速度なら速度の増分 Δv [m/s])。
  内部で 1 kHz などで読んで足し込んだ値です。8 ms に 1 回だけ読む方式より、振動やモータの雑音に強くなります
- **第 2 希望: その瞬間の値**。これでも動きます (今のプロファイルはこの前提)
- **どちらかを教えてください**。こちらの積分の仕方が変わります
- **時刻**: そのサンプルが「SPI の転送の何 ms 前のものか」を教えてください (今の想定は 3.5 ms 前)。
  これがずれると、車輪・vision と噛み合いません。ばらつき (ジッタ) の目安もあると助かります

## 4. バイトの置き場所

今の受け口はこうなっています (20 バイトのフレーム)。

| 位置 | 中身 |
|---|---|
| 0 | ヘッダ 0xFF |
| 1〜3 | 電圧・センサ情報・キャパシタ |
| 4〜11 | 車輪 4 つ (FL, BL, BR, FR) int16 |
| **12〜13** | **gyroZ** int16 |
| **14〜15** | **accelX** int16 |
| **16〜17** | **accelY** int16 |
| 18 | 予備 (0 固定) |
| 19 | フッタ 0xAA |

- 12〜17 は今 0 埋めの領域です。**ここに載せてもらえれば、Pi 側は設定を切り替えるだけです**
- 別の配置にしたい場合も対応できます。オフセットと型を教えてください
- 予備の 18 バイト目は、温度や状態のビットに使えます

## 5. 較正と健全性

- **起動時のオフセット除去**をしているなら、そのやり方を教えてください (静止が必要か、何秒か、Flash に保存か)
- 静止が必要なら、**起動時にロボットを動かさない手順**をこちらでも守ります
- IMU が読めない・壊れているときは、**無効と分かる形**にしてください (センサ情報のビットを 1 つ使うのが簡単です)。
  0 を送られると「止まっている」と誤解します
- 飽和したときも、分かる形にしてもらえると助かります

## 6. 取り付けについて教えてほしいこと

- **向き**: ジャイロ Z の正が反時計回りか。加速度の +X が機体の前か、+Y が左か
- **位置**: 機体の中心からのずれ [mm]。中心から離れていると、回転しているときに遠心の加速度が乗るので、その値で補正します
- **防振**: モータや車輪の近くだと振動を拾います。取り付け位置の方針を教えてください

## 7. 進め方の提案 (リスクを小さく)

1. **まず記録だけ**。IMU の値を SPI に載せてもらい、Pi 側は記録するだけ (制御には使わない)。これならロボットの動きは変わりません
2. こちらで「IMU あり / なし」を同じ走行のデータで比べます (ロボットを動かさずに何度でも比較できる仕組みが既にあります)
3. 効果が数字で出たら、推定に組み込み、その次に角速度の内側のループに使います

## 8. こちらから聞きたいこと

1. 使うセンサは何ですか (旧基板には MPU6500 が載っていた形跡があります。BNO055 も実装だけあります)
2. STM の処理に余裕はありますか (1 kHz で読んで 8 ms ぶん足し込む処理が入りますか)
3. SPI のフレームは 20 バイトのままで良いですか (12〜17 の空きを使う形で足りますか)
4. 載せられるのは全機ですか、一部の機体だけですか (一部なら、プロファイルを機体ごとに切り替えます)

## 補足: なぜ生の値なのか (1 段落)

ジャイロは「予測の入力」、車輪の速度は「観測」として使います。こうすると、タイヤが滑ったときに
「予測 (ジャイロ) と観測 (車輪) の食い違い」として滑りが見え、位置を直せます。逆に、積分済みの角度だけをもらうと、
バイアスも滑りも見えなくなり、混ぜようがありません。設計の根拠は
[`self-localization-plan.md`](./self-localization-plan.md) §3.5〜3.6・§4 にあります。

## 9. 実装の確認結果 (2026-09-23)

読んだもの: `ssl-Circuit` master の仕様書 `MainBoard_V26_2/docs/SPI_PROTOCOL.md` と、実装 (`src/unit/imu.c`, `src/unit/robot.c`)。
**仕様書・ファーム・Pi3 の実装の 3 つで、バイト位置・型・倍率はすべて一致している** (下の表)。

### 入っていたもの (要望と一致)

| 項目 | 実装 |
|---|---|
| センサ | LSM6DSO32 (SPI1) |
| ジャイロ | ±2000 dps。コメントに「±500 dps だと最大角速度指令で飽和する」とあり、こちらの心配と同じ判断 |
| 加速度 | ±4 g |
| 送っている値 | 加速度 X・Y [1 mg/LSB]、**ヨーの角速度** [900 LSB = 1 rad/s]、Madgwick の姿勢角 [0.0001 rad/LSB] |
| バイアス | 起動時に静止で 200 サンプル (約 2 s) 平均して引く |

SPI のフレーム (STM → Pi):

| 位置 | 中身 |
|---|---|
| 0 | ヘッダ 0xFF |
| 1〜3 | 電圧・ドリブラ状態・キャパシタ |
| 4〜11 | 車輪 4 つ int16 (0.01 rad/s) |
| 12〜13 / 14〜15 | 加速度 X / Y int16 (1 mg) |
| 16〜17 | ヨーの角速度 int16 (1/900 rad/s) |
| 18〜19 | 姿勢角 int16 (0.0001 rad) |
| 20 | フッタ 0xAA |

### Pi 側で対応したこと (ssl-RACOON-Pi3)

- **フレームが 20 → 21 バイトに伸びた**ので、Pi は **20 / 21 を自動で見分ける**ようにした。新旧のファームが混ざっていても動く。
  切り替えの間隔は **1.2 s** にしてある: 仕様書 §1 の「STM は 750 ms 進まないと強制的に再同期する」より長くしないと、
  STM が立て直す前にこちらが形を変えてしまい、いつまでも噛み合わない
- 下りのフレームも 21 バイトにし、**19 バイト目は予備として 0 を送る** (§4)。試験で固定した
- IMU の値を `state` に置き、走行の記録 (CSV) にも残す (制御にはまだ使わない)。倍率は §2 のとおり
  (加速度 ×1000 [g] → m/s² に直す、ヨーの角速度 ×900 [rad/s]、姿勢角 ×10000 [rad])
- 記録用のフレーム定義 `rock5a-v2-imu` を仕様書に合わせた。IMU の時刻ずれは、ODR 104 Hz の平均として
  転送の 4.8 ms 前と置いている (実際は 0〜9.6 ms のばらつき。下の「まだ頼みたいこと」2 番)
- **車輪の並びと取付角が仕様書と一致した**: §2 の wheel0〜3 は 55° / 135° / −135° / −55°。
  こちらが vision から同定した値は 55.4° / 136.1° / −136.3° / −57.4° で、**前から疑っていた FL と FR の入れ替わりは無い**と確認できた
- 姿勢角 (`yaw_rad`) は受け取るが**使っていない**。§3 のとおり起動時を 0 とした相対角でドリフトするため、
  こちらは vision と融合した推定を使う

### 電圧のバイトの不具合 (2026-09-23 に判明、ファーム側で修正予定)

満充電の電池 (26〜27 V) に替えたらブザーが鳴り続けた。原因は**電圧のバイトが一周していた**こと。

- `robot.h` の `battery_voltage` は **uint8** なので、まず**小数が落ちて整数ボルトになる**
  (仕様書は「実値 = raw/10」= 0.1 V 刻みと読めるが、実際は 1 V 刻み)
- `dst[1] = battery_voltage * 10` も uint8 のままなので、**26 V → 260 → 4 (0.4 V)、27 V → 270 → 14 (1.4 V)** と一周する
- 実機のフレームでも電圧のバイトは 4 と 14 しか出ておらず (中間の値が無い)、今日の記録も 23.0 / 22.0 / 21.0 / 24.0 V と
  常に整数だった。**V26_1_1 にも同じコードがある**
- Pi はこれを 0.4 V と読み、電池異常としてブザーを鳴らしていた (電池は正常)

**ファーム側は倍率を 0.2 V/LSB (×5) に変更予定**。Pi 側も対応済み:
- 21 バイトのフレーム (v2) は 0.2 V/LSB で読む。20 バイト (v1) は従来どおり 0.1 V/LSB
- 21 バイトでも**倍率を直す前の中間の版**があるので、0.2 V/LSB で 40 V を超えたら 0.1 V/LSB で読み直す
  (こちらの電池は 14〜30 V なので、この境目で確実に見分けられる)
- 電池の判定は生の値ではなく**ボルト**で行うようにした (`state.BatteryVolts`)

**ファーム側へのお願い**: 上限で止める処理も入れてください (`v*5` が 255 を超えたら 255)。
51 V までなら一周しませんが、配線の異常などで大きな値が出たときに、また小さな値に化けるのを防げます。
`battery_voltage` を float にすれば 0.2 V の分解能も生きます。仕様書の「×10」の記述も更新をお願いします。

### 実機で確かめた取り付けの向き (2026-09-23)

`/status` に IMU を出し、ロボットを手で動かして確かめた。

| 試したこと | 実測 | 分かったこと |
|---|---|---|
| その場で反時計回りに 1 周 | ヨーの角速度 +1.0〜+1.8 rad/s、STM の姿勢角が 1 周で +2π | **反時計回りが正** (こちらの約束と同じ) |
| 前 (ドリブラ側) を持ち上げる | 加速度 **Y** が −4.4 m/s²、X はほぼ 0 | **IMU の +Y = 機体の前** |
| 左側を持ち上げる | 加速度 **X** が +5.4 m/s²、Y はほぼ 0 | **IMU の +X = 機体の右** |

→ **IMU は機体に対して 90° 回して付いている**。Pi 側は受け取った時点で直している
(`internal/rock5a/config.go` の `bodyFromImuAccel`: 前後 = IMU の Y、左右 = −IMU の X)。
角速度は面内の回転なので付け替えの影響を受けない。

**静止しているのにヨーの角速度が −0.041 rad/s (−2.4°/s) 残っている。**
STM は起動時にバイアスを引いているが、それでもこれだけずれている。STM 側の姿勢角 (`yaw_rad`) は
この分だけ流れ続ける (1 分で約 140°)。こちらの推定器はバイアスを状態として推定して打ち消すので問題ない。
**起動時のバイアス測定は、機体を完全に静止させた状態で行う必要がある** (持ち上げたり動かしたりしない)。

### まだ頼みたいこと

1. **IMU の更新が 104 Hz** (ODR 104 Hz) で、SPI は 125 Hz。同じ値が 2 回来たり、8 ms の間に更新が無かったりする。
   **ODR を 416 Hz 程度に上げ、SPI 1 回ぶん (8 ms) の平均か積分を載せてほしい**
2. **サンプルの時刻**: 今は「データが用意できたとき」に更新するので、SPI の転送から見て 0〜9.6 ms のばらつきがある。
   **どれだけ前のサンプルかを一定にするか、ばらつきの目安を教えてほしい**
3. **取り付けの向きと位置**: ヨーの角速度の正が反時計回りか、加速度の +X が前・+Y が左か、機体中心からのずれ [mm]
4. **0 埋めが無くなったので、フレームの同期の手がかりがヘッダとフッタだけになった** (仕様書も「予備領域は残っていない」と書いている)。
   Pi 側は「前回と同じ位置を優先する」ようにして誤同期を避けているが、**18〜19 の姿勢角はこちらでは使わない**ので、
   そこを固定の印 (マジックバイト) か温度に替えてもらえると、同期が強くなる
5. **焼く順番の注意**: この新しいファームを焼いた機体は、**古い Pi のプログラム (Pi2 と、対応前の Pi3) とは通信できない**。
   Pi 側を先に更新すること
